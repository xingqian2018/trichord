MoE handbook audit: does our MoE have the problems the handbook describes?

2026-11-05 · Reference: Hugging Face, "The Ultimate MoE Training Handbook" (published 2026-11-05, Megatron-LM based) huggingface.co/spaces/huggingface/moe-blogpost · Method: 10 read-only agents, one per handbook topic, checked against both Megatron trees, every qwen3 golden argv and the logs of about 780 runs (section 7) · No code was changed and no job was submitted · 中文：2026-11-05_moe_handbook_audit.html

In one sentence: the MoE machinery itself has no bug. Router precision, dropless dispatch, aux scaling, the expert bias, and our own KD / MuonH / eval wrappers are all correct. But 5 of the traps the handbook names do apply, and two of them affect conclusions directly: the aux-loss scope changes with the rung (a confound for the ladder extrapolation) and the MuonH router LR does not scale with width (matters for the 235B target at h=4096).

Cheapest next step: an eval-only MaxVio pass on the existing KD q2/q3 checkpoints tells us whether the main line is balanced.

2. Confirmed issues

2.1 Main-line balance is invisible, and LBL≈1 is read as "balanced"

What the handbook says

  • Megatron's aux loss is E·Σ fi·Pi. It equals 1 whenever the router probabilities are flat, whatever the actual load, so read MaxVio (how far the busiest expert is above the mean), not the aux loss (3.3; A.2 "aux loss near 1 but one GPU slow").
  • Read MaxVio at the scope you balance: both per micro-batch and per global batch (A.1).

What we have

  • The main line (KD s64y, s64y_fit, docmask, packplan), BASE v1, Muon and MuonH run without LADDER_ROUTER_HEALTH, and no golden carries --moe-per-layer-logging. The logs contain only a layer-averaged load_balancing_loss. Router health is set only in the dsv3 / swa / router_ne exp files and one prod packplan exp.
  • Main-line LBL is close to 1 everywhere (mean over the last 20% of training):

  • We balance per micro-batch, but router_health.py measures only global-batch MaxVio. Per-micro-batch and per-EP-rank load have never been measured, and the per-EP-rank load is what sets EP step time.
  • Places where LBL is read as a balance measure: DECISIONS.md:1696 says "load_balancing_loss (1.0 = balanced, 128 = one expert)", but for top-8 the upper bound is E/k = 16, so the W3 readings of 14.5–15.7 are close to total collapse onto 8 experts. Recommendation

  • Default new main-line runs to LADDER_ROUTER_HEALTH=100 and --moe-per-layer-logging. Router health costs about 1.07 s per report at q3, once every 100 steps, so under 1%.
  • Run an eval-only LADDER_ROUTER_MAXVIO_VAL=1 pass on the existing KD q2/q3 checkpoints; this answers the question for the main line without retraining.
  • Add per-micro-batch and per-EP-rank MaxVio to router_health.py. Use MaxVio (layer mean and worst layer) as the balance criterion and stop citing LBL.

2.2 Aux-loss scope shrinks with the rung, from 32K to 8K tokens

What the handbook says

  • 3.3 Scope: when a micro-batch is all one domain, forcing balance inside it keeps experts from specializing by domain (Qiu et al., "Demons in the Detail"). Global-batch scope is better for quality at about +5.8% step time. A.2 "experts that do not specialize by domain".

What we have

  • aux_loss counts within one rank (TP=CP=1), so each balancing group is mbs × 8192 tokens. mbs is set per rung (arch_rung_defaults in sh/arch/qwen3moe.sh):

  • Each 8K sample comes from exactly one of 1975 prefixes (BlendedDataset; the kd/data.py docstring says the same for the KD line). So at q5/q6 the aux loss is effectively a sequence-wise Switch loss on a single-domain sequence, at 10× DeepSeek-V3's sequence-wise coefficient (1e-4).
  • Side evidence: DSV3_SWS_AUX1EM3, which raises the sequence-wise coefficient from 1e-4 to 1e-3, costs +0.0078 / +0.0098 / +0.0066 nats at q0/q1/q2. A narrower scope with a larger coefficient does cost LM loss.
  • The README rejected global_aux_loss because its effective strength is 1e-3/DP, which differs across rungs. That claim checks out (identical code in both trees), but the current per-micro-batch scheme also differs across rungs. With GBS fixed at 221, a DP-patched global aux (code/scaling_ladder/tools/patches/global_aux_loss_dp_scale.patch) would be the rung-invariant option.
  • A smaller difference: KD's soft targets send a smaller LM gradient into the router, so the same 1e-3 is relatively stronger under KD. LBL at q1, iter 14680: CE (OPT_MUONH) 1.055, KD α0.8 1.041. The aux gradient scaling itself is identical under CE and KD; this is not a bug.

Recommendation

  • Measure first: mbs 1 vs mbs 4 at q0/q1 with the same GBS.
  • If it matters: all-reduce tokens_per_expert over a fixed-size DP subgroup (e.g. 32K tokens), or switch to the DP-patched global aux. The latter also needs int64 / fp32 counters (see the bf16-counter row in section 4).

2.3 MuonH router LR does not scale with width

What the handbook says

  • 3.6 Optimizer: Muon can destabilize the router; Qwen3.8-Next moved its router back to AdamW, and Megatron offers --moe-router-skip-muon. A.2 "experts collapse layer by layer under Muon".

What we have

  • Muon arm: --moe-router-skip-muon, router on AdamW with wd 0.1. matches
  • MuonH main line: the router uses AdamH (--hyperp-router adam_hyperball) with its norm pinned at 0.02·√(E·h), wd 0, at 1× the hidden LR. The main line sets no HYPERP_GROUP_LR_MULT, so no rung has a router LR multiplier.
  • At h=4096 (the W3 cells) routing collapsed within 50 steps: LBL 14.5–15.9, grad norm up to 511,442, loss up to 10.4. h ≤ 2048 is clean: ≤ 3.8 at step 50, about 1.1 by step 300 (DECISIONS.md lines ~1689–1733).
  • 100-step probe results:
    • router ×0.25: LBL 2.15 at step 100, fixed.
    • router on AdamW: not fixed, LBL 13–16.
    • aux 1e-2: only partly fixed.
    • The RTADAMW arm (AdamW router at the HyperP LR) also collapsed: LBL 3.8–8.2, with 24 and 44 loss spikes.
  • No full-length validation exists: RT0P25 was cancelled before it started, and the DSV3 h=4096 cell is still Planned.
  • Related: the router input is the shared pre-MLP RMSNorm output, with no separate router norm and no 1/√d. The initial logit std is 0.02·√h, which doubles from q0 to q6.

Recommendation

  • Fix a router width rule before 235B: ×0.25, an LR ∝ 1/h, or the DSV3 router. Validate with a full-length h=4096 run with router health on, not a 100-step probe.

2.4 Fixed-step expert bias cannot balance the first MoE layer

What the handbook says

  • 3.3 Loss-free bias: a fixed-step sign update lags a moving router, "loss-free bias run still unbalanced after many steps". Li et al.: at 128 experts and γ 1e-3 the busiest expert sits at about 20× the mean. The handbook's fix is quantile balancing.

What we have

  • All-MoE MUONH_FIT_DSV3, global-batch MaxVio of the first MoE layer (L0) over the middle of the run (10–70% of steps):
q0q1q2q3
L05.455.163.603.30
Other layers0.46–0.52
  • L0 is the most unbalanced layer in 381 of 390 q3 reports, and above 2 in 92% of q3 reports between steps 500 and 40k. It only comes down as the LR decays (0.24–0.69 at the end). The reported "MaxVio 0.15–0.18" is the end-of-run value only.
  • Changing the step does not fix it (SWS, q0, L0 mid-run MaxVio): γ 1e-4 → 6.93; 1e-3 → 3.85; 1e-2 → 4.45 mid-run and 9.21 at the end (it oscillates).
  • The same router on AdamW (BASE_DSV3_ONETREE) keeps L0 at 0.46–0.88, which points to the fast-moving gate under MuonH.
  • What does fix L0:
    • seq-aux 1e-3: L0 drops to 0.80, at a cost of +0.008 to +0.010 nats.
    • A dense layer 0: PROD (dense L0 + shared expert) has its first MoE layer at 0.70–0.84 mid-run and the worst layer at 1.05–1.14 (q4/q5).
  • BIASONLY (no seq-aux) at q3: L0 at 11.97, about 13× the mean, close to the handbook's 20×.
  • The bias does not transfer to eval sets: the DSV3 q1 control is at MaxVio 0.17 in training, 1.98 on val_v2 and 5.05 on codefresh with 93 dead experts.
  • Quantile balancing is supported in both Megatron trees (--moe-router-load-balancing-type quantile_balancing) but blocked by the MOE_ROUTER_LOAD_BALANCING whitelist in sh/arch/qwen3moe.sh (around line 59); router_ne_xx/NOTES.md:123 also records skipping it. Megatron makes it exclusive with every aux loss, so seq-aux 1e-4 would also have to go.
  • The batch-size study is confounded: GBS spans 128× (4 to 512 sequences of 32K) while γ stays at 1e-3 per step, so the per-token bias adaptation rate differs by 128×.

Recommendation

  • QB arm: q0 × 3 seeds plus q1, on both the all-MoE SWS base and the PROD dense-L0 base, with aux coefficient 0, no expert bias, EMA 0 and 0.9. Read L0 and worst-layer MaxVio curves, step time at EP ≥ 4, and R1 val. It needs a one-word whitelist change.
  • Make "mid-run worst-layer MaxVio" the health criterion instead of end-of-run means.

2.5 No node-health or throughput gate, and no profile ever taken

What the handbook says

  • 2.1: run DCGM diag -r 1 and an nccl-tests all-to-all baseline on every allocation, or use Megatron's --gpu-sniff-test-interval. 3.7: trace one step of every new configuration at the node count you will run.

What we have

  • base.sh and submit.sh run no DCGM, no nccl-tests and no sniff test (gpu_sniff_test.py exists in both trees but is unused). The only check is a one-off 2-node all_reduce probe (job 34988: IB, NCCL 2.30.7, 290 GB/s). Bad nodes are excluded only after a failure.
  • Allocations that ran slow for a whole segment, found in the logs:

  • Rack straddling does not explain them: on slurm-2 the q4 segments with 32 hosts in 32 racks were the fastest (jobs 35003 / 36135 / 36137: 1045–1108 ms). Sick nodes or links are more likely.
  • No nsys or torch-profiler trace exists for any production layout; the only profile is the single-node q0 perf run from 10-20. The share of all-to-all and imbalance in step time at EP 8 (q4–q6) is unknown.
  • EP communication overlap is structurally unavailable: q2–q6 run one micro-batch per step, and the KD path refuses --overlap-moe-expert-parallel-comm (kd/forward_step.py:31,52).
  • Step time drifts up 6–8% over training while LBL falls from 1.08 to 1.01: v1 q2 689 → 734 ms, v1 q3 901 → 959 ms, KD q3 1300 → 1407 ms.

Recommendation

  • Add a preflight to base.sh: per-node dcgmi diag -r 1 plus a short all-to-all bandwidth test, or turn on --gpu-sniff-test-interval.
  • Step-time watchdog: after about 200 iterations, if the segment median is more than 15% slower than the rung reference, alert and requeue with --exclude.
  • One 3-step trace at q3 (16 nodes, EP 4) and one at q4 (32 nodes, EP 8), each repeated with --moe-router-force-load-balancing to measure the imbalance cost.

3. Secondary issues

3.1 Rerun is disabled in every run

  • All of the roughly 787 argv files carry --rerun-mode disabled (from the shared argv in sh/base.sh), while both trees default to validate_results. KD needs it off (a replay loses the KD side channel, kd/forward_step.py:17-26); the other arms simply inherit it, and no reason is recorded.
  • The NaN check is still on. In disabled mode a NaN raises a fatal RuntimeError and the process exits with 1, not 16, with no replay on another GPU and no attribution.
  • No consequence so far: 0 NaN/Inf, 0 skipped iterations and 0 rerun messages across 779 runs. The exit codes seen (1, 2, 134, 135, 139, 143) are all infrastructure. At 235B this becomes a risk: a resumed segment can land on the same bad GPU and crash-loop.

  • The handbook's precursor pattern is real here: grad norm and LBL rise 1–3 steps before the spikes, and in the router-collapse cases (wide cells, rtadamw) LBL rises hundreds of steps earlier. All were found after the fact; nothing raises an alarm.
  • MuonH+KD main line (q0–q5) and its packplan variants: 0 loss spikes (a spike = more than 0.1 above the median of the previous 20 logged points).
  • No run uses --save-activations-interval and there is no expert-output hook. router_health.py tracks load, MaxVio and logits only, and the MuonH sphere monitor tracks weight norms. Under MuonH weight norms are pinned, so a rogue expert could only show in activations.
  • Main-line grad-norm jumps (worst: KD s64y q3 17.9 at step 55070, 40× median; packplan q2 56.3 at 28740, 111×) are absorbed by clip 1.0 with no loss effect. 57% of them fall on the same iteration across independent runs (55070, 10690, 35940, 56820, each in 13–19 runs), so they come from the data order, not hardware or numerics.

3.3 Softmax router logits drift upward, no z-loss

  • z-loss is off on purpose to match Qwen3 (qwen3moe.sh:47,146); the gpt-oss ladder used 1e-3.
  • max|z| keeps rising: MUONH_FIT q1 2.3 (step 1) → 17.8 (1k) → 30.5 (10k) → 35–39 (end); MUONH_FIT_SWA q3 4.2 → 44.3, with the share of logits above +4 going from 0 to 81%. The signed monitor (job 1377911) shows it is entirely a common upward offset, which is the case where the handbook says to add z-loss. Sigmoid routers go higher: DSV3 q3 about 175, PROD1/RS1 63–159.
  • The router runs in fp32, so there is no precision risk, and main-line q3–q5 show no spikes. But main-line q3+ runs have router health off and logsumexp is never logged (Megatron logs it only when the coefficient is non-zero).

3.4 Gate sharpness has never been measured

  • No top-1 weight, Max1/Max2 or entropy is logged for the softmax router (router_health.py's "top-8 pinned" metric is sigmoid-specific). The only proxy is the full-softmax entropy on the phi-loss q0 arm: 3.4–4.2 nats (ln 128 = 4.85), which looks flat. The handbook's test: Max1/Max2 → 1 means the layer averages its top-k (3.1 Sharpness).
  • Router init is N(0, 0.02) at every rung (hyperp/init.py:11, Qwen3's value), with no jitter and no logit normalisation.

3.5 Rarely used experts take oversized steps under MuonH

  • MuonH updates X −= lr·‖X‖F/‖U‖F·U, which fixes each step's Frobenius size whatever the gradient rank. So the handbook's point that a per-expert step shrinks when an expert sees few tokens does not hold for us.
  • CPU check (q3 fc1 960×1280, lr 7.01e-3, quintic NS): step spectral norm over weight spectral norm is 0.116 for a rank-1 gradient vs 0.0044 at full rank, 26× larger.
  • An expert with zero tokens keeps stepping at full lr on stale momentum for about 300 steps, a total displacement of roughly 2× its radius; under AdamW the step dies out in about 50 steps.
  • Whether this bites is unknown: the main line has no per-expert telemetry.

3.6 Other

  • bf16 Newton-Schulz: both paths run NS in bf16 (MuonH ns_dtype=torch.bfloat16, hyperball_batched.py:276; Muon --muon-fp32-matmul-prec defaults to medium). No spike attributable to it was seen.
  • PROD v1 design controls:
    • The shared expert is added on top of top-8, +12.5% expert compute, with no ablation. The handbook recommends replacing one routed slot for a fair test.
    • latent2 is compared at equal tokens: at q3 N_active is +7.3% and FLOPs/token +3.8%, so about 0.003 of the −0.011 q3 gain is extra compute. Routed scale 2.5 has no effect under latent (RMSNorm sits before fc2_latent_proj).
    • e2x and latent2 run 13–39% slower; compare them at equal wall time too.
    • Dense L0 is booked as an MoE layer, so N_total is overstated by 3–8%.
  • Memory logged for DP rank 0 only (report_memory): the W3/W4 memory gates were decided on rank-0 peaks. Headroom is fine today (KD q3 about 150 GB of about 284 GB); watch it for wider cells and 235B.
  • q0 runs at 47 TFLOP/s/GPU: TE 2.19's CUTLASS grouped GEMM is SM90-only, so GB300 falls back to a per-expert cuBLAS loop. This is a throughput issue, not a quality issue; the granularity itself is at the handbook's plateau.
  • No dense reference and no deterministic mode: low impact. Multi-seed statistical acceptance, CPU parity tests and the DP weight-hash check cover most of it.

5. Tool and doc errors

  • dsv3/tools/bias_spread_trend.py: router-health per-layer lines wrap at about 1 KB (continuation lines start with " 0: "), so the tool reads only the first 14 of 18 / 24 / 30 layers at q1 / q2 / q3. DECISIONS.md line ~1997, "every arm PASSES the hard criterion (largest spread 0.59)", relied on it. Re-parsing DSV3 A q1–q3 puts the worst spread (0.34 / 0.31 / 0.32) inside the first 14 layers, so A's verdict holds; other arms are unchecked.
  • DECISIONS.md:1696: the LBL upper bound is 16 for top-8, not 128.
  • README "init 0.02" is incomplete: under AdamW fc2 uses 0.02/√(2L) (0.0041 at q0, 0.0020 at q6); Qwen3 HF uses 0.02 throughout.
  • README throughput numbers (q2 264, q3 338 TFLOP/s) are early-run; full-run medians are 3–7% lower (v1 q2 254, q3 314).
  • README says "no compensation outside --calculate-per-token-loss"; the per-token branch is also 1/DP.
  • router_maxvio_doc_isolated.json counts pad tokens (documented in router_health.py).
  • A second, conda-forge libnccl.so.2.32.3 sits in boxiangw/envs/dpl/lib, a latent shadowing risk (torch currently loads pip's 2.30.7 via RPATH).

6. Recommendations

6.1 No GPU needed

  1. Default new main-line launches to LADDER_ROUTER_HEALTH=100 and --moe-per-layer-logging. base.sh is sourced live when a job starts, so edit it between submissions.
  2. Extend router_health.py with per-micro-batch and per-EP-rank MaxVio, RMS logsumexp, top-1 weight and Max1/Max2, and the max/median of per-expert fc2 output norms.
  3. Add the node preflight and step-time watchdog to base.sh; set NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET on rank 0; log memory as an all-reduce MAX.
  4. Fix the doc and tool errors in section 5.
  5. Switch non-KD arms back to --rerun-mode validate_results; keep it off for KD and document why.
  6. Dump the samples at steps 55070 / 56820 / 28740 and check them for bad documents.

  • Every agent was read-only. Scope:
    • both Megatron trees: fork @60547a3f4 (AdamW BASE, Muon) and ADLR @80781ab0ab (MuonH, KD);
    • the launch layer (our clone and the shared copy jobs actually source, which differ only in QOS lines);
    • print-mode argv renders and goldens;
    • argv, logs and tensorboard of about 780 runs under boxiangw and xingqianx;
    • DECISIONS.md and the reports.
  • Cross-checks: the rung-dependent aux scope was found independently by agents 4 and 10; the L0 imbalance by agents 1/3/4/5/8 from different runs; the router LR problem by agents 2/7/8. I also spot-checked the mbs table in qwen3moe.sh, the load-balancing whitelist, --moe-router-dtype fp32 (line 183), DECISIONS.md:1696 and --rerun-mode disabled in base.sh; all match the agents' reports.
  • Limits:
    • Most numbers come from the agents' log parsing and were not all re-checked independently.
    • The shared copy's DECISIONS.md is not readable to us; the clone's version was read.
    • The main line has no per-layer data at q2 or above, so section 2.1's conclusion for the main line is inferred from MUONH_FIT / SWA runs with the same router. The P0 eval-only MaxVio pass would verify it directly.
