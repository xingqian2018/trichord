Doc-isolated (iso-doc) eval guide: what it measures, result format, where things are, how to run it

1. What the eval measures

Definition: every validation document becomes its own sample, with no context from any other document. For every token of the document the negative log-likelihood (NLL) of predicting it is computed, and these are averaged. The validation inside training packs documents end to end into the window, so documents see each other; doc-isolated scoring does not have this, which makes models with different packing or training length comparable.

Scoring rule (code: scripts/doc_isolated/ in the harness repo, see 4.3):

  • Every document is scored on its own and never sees another document (how, see "Two implementations" below).
  • For a document of N tokens (its final EOD included) the inputs are tokens 1 to N−1 and the labels are tokens 2 to N. The first token is never predicted and the EOD is never a target, so a document has N−2 predicted tokens.
  • A document with more predicted tokens than the window is cut into consecutive chunks. Each chunk is its own sample and starts without the previous chunk's context.
  • The loss of a split is the mean NLL over all predicted tokens of that split (token-weighted).

Two implementations, identical scores:

  • packed (the new method, default since 2026-11-13): every row is 32,768 tokens wide and holds several documents, kept apart by the model's own segment isolation (cu_seqlens). One job and one model load per checkpoint, running the three passes of the table below. 8K result = S + L8, 32K result = S + L32.
  • padded (the old method): one document per row, padded up to the window length. Now used only to reproduce an old result.
Pass Documents Segment length Gives
S Those with ≤ 8,192 predicted tokens, packed One per document Their score for both windows
L32 The remaining long documents, cut into 32K chunks, packed 32,768 Their 32K score
L8 The same rows as L32 8,192 Their 8K score
  • The two implementations were compared split by split: the 59B at steps 10,000 / 20,000 / 24,000, both windows, 690 splits; ladder checkpoints OPT_MUONH q1 (trained at 8K without document masking) and PROD1_DPSK q1, 345 splits. Token counts identical everywhere, largest loss difference 1.2e-7.
  • The new method does not depend on how the checkpoint was trained: the eval always turns the segment isolation on (--dataloader-inter-document-masking, changes no weight) and always uses 32K rows.
  • Cost: one 59B checkpoint takes about 1 hour on one node (old method: about 13.6 node-hours); a ladder q1 about 15 minutes.

Two windows:

Window Length Use
8K 8,192 Comparable with every earlier result; the default for comparisons
32K 32,768 Matches the training length of models trained at 32K
  • Both windows score exactly the same tokens; they differ only in how long documents are cut. A document shorter than 8K gives the same result at both windows; a long document has more context at 32K and a lower loss.
  • Do not read the 32K result of a checkpoint trained at 8K: it never saw positions beyond 8,192 and its loss gets clearly worse (measured: for the 8K-trained KD_MUONH_A0P8_S64Y_FIT_DOCMASK q0–q2, overall_tsqw at 32K is 0.18–0.40 higher than at 8K). The new method gives only the 8K result for a checkpoint trained shorter than 32K.
  • Both windows must come from one model load (the user's rule of 2026-11-04): the new method runs the passes S, L32 and L8 in one job.

2. Metrics

Every metric has three numbers: loss (nats per token, lower is better), ppl = exp(loss), and bpb (bits per byte) = loss × tokens ÷ (bytes × ln 2).

Metric key Display name Definition
00_overall_tsqw overall_tsqw Headline metric. The token-weighted loss of each of the 7 collections, averaged with weights proportional to the square root of the collection's token count
00_overall_tw overall_tw All tokens of 6 collections (pile_10k left out) pooled and averaged
00_overall_macro overall_macro Plain mean of the losses of those 6 collections
01_val_v2_overall_tw val_v2 The cc + python + arxiv suites pooled, token-weighted
01_val_v2_cc / _python / _arxiv the three parts of val_v2 Each part's loss
02_uncheatable_tw uncheatable 55 splits, token-weighted
03_codefresh_tw codefresh 30 splits, token-weighted
04_v3small_tw v3small 8 splits, token-weighted
04_private_internal_tw private_internal 2 splits, token-weighted
05_pile_test_tw pile_test 16 splits, token-weighted
05_pile_10k_tw pile_10k 1 split
02_uncheatable_macro, 04_v3small_macro, 05_pile_test_macro (macro) Plain mean of the split losses of that collection, not token-weighted

Rules for comparing:

  • Compare loss between models with the same tokenizer. Our models, the Qwen3 family and MiMo share the same token ids.
  • Between models with different tokenizers compare only bpb. The overall_tsqw weights use the Qwen3 token counts for every model.
  • Compare new results with old ones at the 8K window.

3. Result file formats

3.1 Full result: one checkpoint, one window, one JSON

File name <Change ID>_<rung>.json, about 14 KB. Results of the new and the old method have exactly the same fields.

  • Change ID: the experiment's name, for example PROD1_DPSK_LATENT2_E2X_QBK3.
  • rung: q0–q6 are the model sizes of the ladder; ref marks an external model; it<N> marks the checkpoint at iteration N of a production run.
  • Window: a 32K result has _W32K in its Change ID, for example PROD1_DPSK_LATENT2_E2X_QBK3_W32K_q3.json. The file has no separate window field; the eval window is recorded in train.seq_length (that field holds the --seq-length of the eval, not the training length).
Field Content
change, rung Change ID and rung, as in the file name
iteration Training iteration of the checkpoint (0 for an external model)
protocol Always doc_isolated
checkpoint Full path of the checkpoint (the HF model directory for an external model)
eval_job, eval_dir, evaluated_at Slurm job id, raw eval directory and finish time of the eval. With the new method eval_dir is the directory of that window's long-document pass (<ID>__PKL8-… or <ID>__PKL32-…); for an old-method eval run in three parts it is part 1's directory and eval_job the largest job id
train lr, min_lr, train_iters, num_layers, hidden_size, global_batch_size, seq_length from the eval arguments; null for an external model
metrics The 16 metrics of section 2, each {loss, ppl, bpb}
suites The 9 suites, each with loss_tw (token-weighted loss), tokens and splits (every split's loss and tokens)

For an external model with its own tokenizer, every suite and split in suites also has bytes and bpb.

3.2 Pooled result (Boxiang's evals, not shown in the report)

Before 2026-11-13 the production run (59B, ULTRA59B_MUONH_KD_QBK3) had only 5 results of this kind (steps 4,000 / 10,000 / 18,000 / 20,000 / 24,000, 8K), from the evals Boxiang runs as loss-parity reference of the downstream eval. The 59B now has full results (3.1); these pooled results stay in their files and are not shown in the report. Such an eval puts all documents of a collection into one validation set, so a collection has one loss and no split detail. The scoring code is the same as in 3.1 and the document and token counts equal those of our collection of the same name, so a collection's value is the same quantity.

File, in the ladder repo: results_xx/prod_isodoc/<RUN>[_W32K]_iter<7-digit iteration>.json:

Field Content
run, iteration, window Run name, iteration, eval window (8192 or 32768)
pooled_sets Always true
checkpoint, train Checkpoint path; training configuration (total iterations, training length, layers, KD teacher, ...)
metrics Only the collections that were scored, with the keys of 3.1 (now 01_val_v2_overall_tw and 04_v3small_tw), plus tokens, docs, set
not_scored Keys of the collections not scored
source Eval directory, job id, time, who ran it, the Megatron and ladder code used
other_evals Other evals of the same checkpoint and window (only the newest one is used)

3.3 The files of a model in the new folder

~/runs/cosmos_eval_doc_isolate/<category>/<model>/:

File Content
summary.md For people: every metric in one table, one pair of loss / bpb columns per window
summary.json The same numbers: windows.<window>.metrics.<metric key>.{loss, ppl, bpb}, and per window eval_job, evaluated_at, what (full or pooled result)
identity.json What was evaluated: checkpoint, iteration, train, protocol; evals.<window> records the result file's name, the job id, the raw eval directory and where the result file was copied from
breakdowns/<window>.json The complete result file of that window, an unchanged copy of the JSON of 3.1 or 3.2. Window names are 8k, 16k, 32k
runs/<directory name> Links to the raw eval directories

The window name is taken from the result file's train.seq_length, so a model evaluated at 16K shows 16k.

5. How to run it

5.0 Common to all

  • Cluster oci-jhb-slurm-2, account cosmos_base_training. Every eval job uses 1 node with 4 GPUs.
  • Submit from a frozen copy of the code, so that editing the repo cannot change the code under a running job:
S=~/runs/ladder_doc_eval/code_snapshots/doc_isolated_$(date +%Y%m%d_%H%M)
rsync -a --exclude __pycache__ ~/Project/lm-evaluation-harness/scripts/doc_isolated/ $S/ && cd $S
  • Run with --dry first to see what would be submitted, then without it.
  • The new method is the default: one job per checkpoint, giving all the windows due.
  • EVAL_QOS=normal is rewritten to normal_quota on slurm-2. The script uses wckey p0 by default (the user's rule of 2026-11-13); p0 preempts p1 jobs of the same QOS, for example the tc_full teacher-cache tasks (they requeue by themselves). This is the state of 2026-11-13; cluster rules change often, check before submitting.

5.1 A ladder checkpoint

EVAL_QOS=normal EVAL_EXTRA_ARGS= bash run_doc_eval.sh --dry <ID>/q3=run:<absolute path of the run directory>
  • The Change ID has no _W32K. A checkpoint trained at 32K (or longer) gets an 8K and a 32K result, the 32K one written as <ID>_W32K; one trained shorter gets 8K only.
  • How to name the checkpoint: =run:<run directory> (the run's last checkpoint); =p:<ID> (a promoted Change ID); no = takes the promoted directory of the same name.
  • Job name xxdoc-<ID>__PK-<rung>.
  • Checkpoints with sliding-window attention (SWA_FIT_SINK_*) have not been run with the new method yet: compare one against the old method first (compare_packed_padded.py).

Environment variables:

Variable Effect
EVAL_QOS=normal The QOS. Unset means hero-res, which slurm-2 does not have
SBATCH_WCKEY Priority, p0 by default
EVAL_LADDER_CODE=<dir> The ladder code tree; must be the one the run was trained with (the PROD1 overlay trees)
EVAL_EXTRA_ARGS="--flag value" Rewrites eval arguments, for example --distributed-timeout-minutes 240
EVAL_TIME=HH:MM:SS The time limit as given. Unset: per rung as below; 3 hours for a production run's it<N>
EVAL_CACHE_PER_JOB=1 Each job uses its own dataset index cache instead of the shared one
EVAL_RUN_ROOT=<dir> Writes the eval directories elsewhere (for tests, under ~/runs/ladder_doc_eval_speedtest/; the collectors do not read it)
EVAL_PACKED=0 Use the old method. Setting any of the old method's EVAL_DUALWIN_SEQ=8192 (an 8K window from the same load; the Change ID then needs _W32K), EVAL_SPLIT3=1 (three parallel jobs), EVAL_ONLY_PARTS=2 selects it as well

Time limits without EVAL_TIME (set for the old method; the new one needs far less): q0 2:30; q1, q2 3:30; q3 4:30; q4 5:30; q5 8:00; q6 12:00. Measured with the new method: ladder q1 13–17 minutes, the 59B 1:01.

5.2 A checkpoint of a production run

A production run has no checkpoint directory like the ladder's. Stage one first, then use the same submit script:

BX=/scratch/fsw/portfolios/cosmos/projects/cosmos_base_data/users/boxiangw/cosmos_ultra_pre   # Boxiang's production directory, read-only

# 1. stage: writes argv.txt, run.json and a link to the checkpoint under OUR directory, prints the directory
python3 stage_prod_ckpt.py --view $BX/runs/eval59/view/ultra59b_muonh_kd_qbk3 --iter 30000 --change ULTRA59B_MUONH_KD_QBK3

# 2. submit: the rung is it<iteration>
EVAL_QOS=normal EVAL_EXTRA_ARGS= EVAL_CACHE_PER_JOB=1 \
bash run_doc_eval.sh --dry ULTRA59B_MUONH_KD_QBK3/it30000=ckpt:$HOME/runs/ladder_doc_eval/stage/ULTRA59B_MUONH_KD_QBK3/ckpts/it30000
  • One call per checkpoint. Several checkpoints in one call form a chain: each waits for the previous one to end.
  • The staging script drops the training-only arguments (pack plan, wandb, ...) and has no training dataset, so the eval never builds a training-set index.
  • The model arguments are identical to those of Boxiang's 59B eval (checked one by one on 2026-11-13).
  • Measured: steps 10,000 / 20,000 / 24,000 took 1:00–1:01 each on one node; both windows agreed with the old method split by split.

5.3 An external model

Scored offline with vLLM, one document per sequence, by the same rules; every split's token count is checked against the ladder's records. The new method is for Megatron checkpoints only.

sbatch -N 1 -t 08:00:00 --export=ALL,NAME=<name>,MODEL=<HF model directory>,PP=1 mimo_doc_eval.sbatch
  • 32K window: add SEQ=32760 and name it <name>_W32K.
  • A model with its own tokenizer: add HFO='{}' EXTRA="--text-dir ~/data/eval_ppl_decon", plus --bos if it needs a BOS token. Such a model's loss is per its own tokens; compare bpb only.
  • Large models use 2 nodes (-N 2, PP=2). The exact arguments used for each model are in the comments at the top of mimo_doc_eval.sbatch.
  • Output directory ~/runs/cosmos_eval_doc_isolate/_runs/<name>-ref-<job id>/.

5.5 Collect, organise, publish

The easiest way is a waiting script in tmux, started after submitting: whenever a job ends or a new result appears it collects, organises and publishes the prod iso-doc tab:

tmux new -d -s iso_finish "bash finish_when_done.sh <job id> [<job id> ...]"   # log ~/runs/ladder_doc_eval/sbatch/finish_<first job id>.log

By hand (in scripts/doc_isolated/ or its frozen copy):

python3 collect_doc_eval.py        # raw directories -> result JSONs (trichord first, then the two copies)
python3 collect_prod_isodoc.py     # the production run's pooled results -> results_xx/prod_isodoc/
python3 organize_doc_isolated.py   # result JSONs -> ~/runs/cosmos_eval_doc_isolate/
cd ~/Project/cosmos_llm_scaling_ladder/reports_xx
python3 gen_eval_html.py --only prod                                       # republish only the report's prod iso-doc tab
rsync -a --exclude __pycache__ ./ ../../trichord/reports/dense_pretrain/   # the report's mirror
  • collect_doc_eval.py takes, per (Change ID, rung, window), the eval with the newest job id: for the new method a window is collected as soon as pass S and that window's pass (L32 or L8) have their results, so the 32K result reaches the report about 17 minutes before the 8K one; for the old method all 3 parts must be done at the same iteration. Every split's scored-token count is checked against the suite yaml.
  • New vs old method: python3 compare_packed_padded.py <ID> <rung> [<rung> ...]; exit status 0 means everything agrees.
  • Several sessions build the report together: publish only your own tab with --only <tab>, never rebuild the whole report.

5.6 What to check first when something goes wrong

Symptom Check first
The job exits at once with LUSTRE CHECK FAILED in its log The node's Lustre is stuck. Add the node name to ~/runs/ladder_doc_eval/lustre_stuck_nodes.txt and resubmit; submissions avoid it from then on
The job hangs at its first file read Same as above (nvl72d007-t01 on 2026-11-13, OST0157/0158)
No output for a long time, then an NCCL timeout Zero-byte files in the dataset index cache: find ~/runs/ladder_doc_eval/data_cache/corpus_v2 -name '*.npy' -size -128c
The job stays PENDING with reason requeued held scontrol release <job id>
Some jobs of one batch get preempted and requeued The batch has mixed wckeys; p0 preempts non-p0 jobs in the same QOS

The job shows PREEMPTED slurm-2 requeues it and it still finishes; it has not ended

A checkpoint has no result JSON New method: whether __PKS, __PKL8 (and __PKL32) all have eval/val_splits_*.json; old method: whether all 3 parts have one, at the same iteration
