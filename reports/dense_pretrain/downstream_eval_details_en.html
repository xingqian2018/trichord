Downstream evaluation details

This document records how we run the downstream tasks today: the settings of every task (temperature, top-p, top-k, generation cap, samples per question, stop strings) and how they compare with the official or commonly used settings.

  • It is a record only. It changes no evaluation setting. Decision (2026-11-13): the current method and settings stay as they are, and the existing baselines are not re-run.
  • The task list is cosmos_ultra_ladder: 36 tasks, 66 scores. Every model uses the same list.
  • The settings are taken from the records the evaluation stored, that is, the values actually sent to the model. The example is the Qwen3.8-Max run.
  • Last updated: 2026-11-13.

1. Settings shared by all tasks

Item What we do
top-k Not used by any task. The request does not carry this parameter
top-p Only three tasks send it: HumanEval 0.95, LiveCodeBench 0.95, MBPP 1.0 (which cuts nothing). The other tasks do not send it and sample from the full distribution
Sampling defaults shipped with a model Not used. The servers of the reference models are started so that only the sampling parameters in the request apply. For our own checkpoints we checked before the evaluation that a request without parameters uses the full distribution
Server length limit 16,384 tokens (prompt plus generation)
Random seed for the few-shot examples 1234, recorded in every score file
Seed of the sampled tasks Sample number r uses seed r, so sampled results can be reproduced

The two kinds of task handle truncation differently:

  • Multiple choice (13 tasks): the model writes nothing. The prompt plus the option may be up to 16,383 tokens long. The longest MMLU prompt we measured is 3,097 tokens, so no question is cut. The old evaluation flow used the default limit of 2,048, and with it 373 MMLU questions lost their beginning.
  • Generation (23 tasks): the prompt is sent whole and is never cut. What the model writes has a cap (see "generation cap" in 2.1) and is cut off there. It is also cut at a stop string.

LCB here means LiveCodeBench (competitive programming problems). There is also a LongCodeBench (a whole code repository in the context, up to 1 million tokens) with the same abbreviation. We have never run it.

3.3 How the prompt is built

We use the official format for base models (not chat models): one fixed example problem with its reference program, then the problem under test, ending right after ### Answer.

### Question
(statement of the example problem)

### Answer

(reference program of the example problem)

### Question
(statement of the problem under test)

### Answer

A function-completion problem has an extra ### Starter Code block after the statement, with the function signature. Each of the two problem types has its own fixed example problem.

Prompt length (Qwen3 tokenizer): median 1,412 tokens, longest 2,935 tokens, far below the server limit of 16,384, so no problem is cut.

3.5 How an answer is judged

  1. The model's answer, with leading and trailing whitespace removed, is run as a program as it is. Markdown code fences are not removed. This is the official handling for base models.
  2. The tests are the public examples plus the hidden tests. A program passes only when it passes all of them. A problem has 1 to 103 tests, median 13.
  3. Standard-input problems: the input is fed to the program and the output is compared line by line (after removing leading and trailing whitespace; when the lines differ, they are compared once more as numbers).
  4. Function-completion problems: the model's function is called, and the return value must equal the expected value.
  5. Each test has a time limit of 6 seconds. There are five outcomes: passed, wrong answer, timed out, runtime error, error in the test program.
  6. 16 processes judge in parallel, and each test process may add at most 16 GB of memory.

How the scores are computed:

  • Pass rate (1 program): problems passed divided by 1,055.
  • Pass rate of a single program (32 programs): per problem, the share of the 32 programs that pass, averaged over all problems.
  • At least one of 32 passes: problems where at least one program passes, divided by 1,055.

The score file also gives the pass rate by difficulty (easy, medium, hard). These are not among the 66 scores.

4. HumanEval and MBPP: comparison with public practice

Apart from the original papers, these two benchmarks have no single agreed setting. The table puts the commonly cited ones side by side.

  • Original paper: the method of the benchmark's authors. HumanEval is from OpenAI's Codex paper of 2021, MBPP from a Google paper of 2021.
  • Upstream lm-eval: the public original of our evaluation framework, with the tasks it ships.
  • EvalPlus: a public code evaluation tool and leaderboard.
  • bigcode: the evaluation tool of the BigCode leaderboard.

4.1 HumanEval

Item Ours Original paper Upstream lm-eval EvalPlus bigcode
Temperature 0.2 0.2 for the single-sample pass rate no sampling no sampling 0.2
top-p 0.95 0.95 none not set 0.95
top-k not used not mentioned none not set off
Generation cap 512 not specified 1,024 768 512
Samples per problem 32 200 1 1 200
  • The original paper writes 200 samples per problem because it reports "at least one of 100 passes". The single-sample pass rate alone does not need that many.
  • Generation cap: the original paper specifies none. Our 512 is the tightest of these. Whether bigcode's 512 includes the prompt is not clear from its documentation.

4.2 MBPP

Item Ours Original paper Upstream lm-eval EvalPlus bigcode
Temperature 0.5 0.5 no sampling no sampling 0.1
top-p, top-k neither used neither mentioned none not set top-p 0.95
Generation cap 768 not specified not set 768 512
Samples per problem 32 80 1 1 15
Examples problems 2, 3, 4 the dataset README names problems 2, 3, 4 problems 2, 3, 4 another prompt
  • The main metric of the original paper is "solved when any one of 80 samples passes". It reports no single-sample pass rate. Our counterpart is "at least one of 32 passes", but the number of samples differs, so the two cannot be compared directly.
  • The problem set differs: the original paper uses 500 test problems, we use the hand-verified subset of 257.
