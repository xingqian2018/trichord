## 7. 已知问题 / 运营状态

- **Boxiang 的 run 都没有用我们合进去的评测设置**（10-22 18:30 核对，148 个 run 的 argv）：没有一个打开 `VAL_PER_SPLIT=1`（9 个 decon suite 按 split 算，含 private_internal，输出 dpl 的 tw / macro / overall），也没有用 `EVAL_AT_ITERS` / `EVAL_TPP_STEP`。
  他用的是自己的协议：6 个合并验证集（val_v2 不拆 cc / python / arxiv，没有 private_internal），in-loop eval 固定每 3500 步一次，事后再补 doc-isolated eval。所以本报告的数和 dpl 的指标不能直接对比。
- **所有 q4 暂停**（14:3x，用户："等存了ckpt之后全停"）：q4 太慢（MuonH 系 1.34–1.40 s/it，单个 run ~41 h，5 个 run 共占 160 节点），先把节点让给 q0–q3 的工作。
  每个 run 都在存完 checkpoint 后停，续跑 = 重新提交 chain。所以优化器和 KD arm 目前只有 q0–q3 可以用来拟合。
- **q5 暂停**：Muon / MuonH q5（00:40，用户），KD q5 ×3（11:30，Boxiang：每 20k 步被 hash check 打断太浪费 64 节点）。只有 BASE q5 在跑。
- **EP 8 下 MuonH 的 DP 副本分叉：已有 workaround**：`pretrain_hyperp.py` 加了每 1000 步一次的参数和优化器状态 re-sync。KD 0.9 q4 用 re-sync 后通过了 20000 步的 check，drift 为 0。
  遥测结论：drift 只出现在 4 个 EP 组上，这 4 个组的两个节点在同一个 rack（跨节点 NVLink 域）；跨 rack 的 12 个组从不 drift；每 1000 步只有 1–2 个 bf16 ulp；和 checkpoint 保存无关。
  **MNNVL 假设已被否定**（17:1x）：在 16 和 128 rank 上用训练时的 NCCL 环境做 fp32 all-reduce 的 bit 测试，MNNVL 开 / 关都试了，没有一个 rank 和 rank 0 不同。
  新的主要怀疑对象：`--overlap-grad-reduce` 下的时序竞争——某个 rank 在 bucket 的 all-reduce 完成前就读了 main-grad，同 rack 的 EP 组时序不同所以更容易撞上。
  计划用 q4 layout 跑 overlap 开 / 关各约 2000 步的对照（每 100 步 re-sync）来验证。**MuonH q0–q3（EP 4）不受影响。**
